# RBXDrop — макет публичной части

Кликабельный макет marketplace по продаже Robux и аккаунтов Roblox. Бэкенда нет:
данные лежат в моках, оплаты и авторизации не существует. Задача макета — утвердить
визуальный язык и воронку покупки до того, как в проект вложатся деньги.

Стек взят боевой из ТЗ, чтобы вёрстку не пришлось переписывать при переходе к
настоящему сайту: **Next.js 16 (App Router) + TypeScript + Tailwind v4**.

## Запуск

```bash
npm install
npm run dev
```

Сборка и проверки:

```bash
npm run build      # статический экспорт в out/
npx tsc --noEmit   # типы
npm run lint       # ESLint
```

## Публикация

Живая версия: **https://kannurali.github.io/rbxdrop/**

Каждый push в `master` запускает `.github/workflows/pages.yml`: сборка с
`output: "export"` и публикация каталога `out` на GitHub Pages. Сайт живёт в
подкаталоге, поэтому в workflow задаются `NEXT_PUBLIC_BASE_PATH=/rbxdrop` и
`NEXT_PUBLIC_SITE_URL`.

Посмотреть сборку локально ровно так, как её отдаст Pages — из подкаталога и
с отдачей `404.html` на неизвестные пути:

```bash
npm run build && npm run preview:pages
```

Дальше открыть http://localhost:4173/rbxdrop/

### Что накладывает статический экспорт

Сервера нет, поэтому в проекте не должно появляться Server Actions, route
handlers с чтением запроса, `cookies()`, редиректов и рерайтов из конфига, а
у каждого динамического маршрута обязан быть `generateStaticParams`.

Два места сделаны именно под это ограничение:

- `/checkout` читает `?account=<id>` на клиенте — серверный `searchParams`
  сделал бы страницу динамической;
- `/order/[id]` предсобран только для демонстрационных заказов из моков.
  Заказ, оформленный прямо в браузере, получает случайный номер, страницы под
  него в сборке нет, и Pages отдаёт `404.html` — он разбирает адрес и
  показывает нужный заказ. На боевом сервере этот обходной путь не нужен.

  В devtools такой заказ виден как ответ 404 — это не поломка, а сам механизм:
  статус отдаёт Pages, а содержимое страницы собирается на клиенте.

  У такой страницы остаётся заголовок вкладки от корневой: метаданные считает
  Next, и перебить их из клиентского компонента не выходит. Содержимое заказа
  при этом полностью на месте. Предсобранные заказы из моков — например
  `/order/RBX-48213/` — показывают правильный заголовок.

## Страницы

| Маршрут | Что там |
|---|---|
| `/` | Hero с живой карточкой покупки, номиналы, способы получения, шаги, аккаунты, FAQ |
| `/rbx` | Полный каталог номиналов и выбор способа получения |
| `/accounts` | Каталог аккаунтов с фильтрами по цене, уровню, предметам, limiteds и возрасту |
| `/accounts/[id]` | Карточка аккаунта: характеристики, состав, цена, наличие |
| `/checkout` | Заказ слева, данные покупателя справа. `?account=<id>` — покупка аккаунта |
| `/order/[id]` | Страница заказа со статусом и полосой прогресса |
| `/account` | Личный кабинет: заказы, профиль, тикеты |
| `/faq`, `/support` | Вопросы и форма обращения |
| `/login`, `/register` | Формы-заглушки |
| `/terms`, `/privacy`, `/refund` | Юридические тексты из футера |

Бренд-анимация на входе показывается один раз за сессию, пропускается кликом или
клавишей и не запускается при `prefers-reduced-motion`.

## Что здесь мок

Всё состояние живёт в `sessionStorage` и в файлах `lib/mock/`:

- номиналы и цены — `lib/mock/packs.ts`;
- способы получения и комиссии — `lib/mock/methods.ts`;
- аккаунты — `lib/mock/accounts.ts`;
- заказы и тикеты — `lib/mock/orders.ts`.

Оформленные в браузере заказы складываются в `sessionStorage` и видны на странице
заказа и в кабинете до закрытия вкладки.

## Что обязательно переносить на сервер

Это не «пожелания на будущее», а места, где макет намеренно упрощён и где ошибка
стоит денег.

1. **Расчёт цены.** Вся арифметика собрана в `lib/pricing.ts` и считается в браузере.
   На бою модуль переезжает на сервер: клиент присылает id номинала и id способа, а
   цену определяет сервер. Если принимать сумму из тела запроса, покупатель оформит
   10 000 Robux за один цент.
2. **Статус оплаты.** В макете заказ сразу получает статус «Выполняется». На бою
   `Paid` ставит только webhook платёжной системы, а не возврат пользователя на сайт
   (ТЗ п.20). Webhook должен быть идемпотентным, иначе повторная доставка события
   выдаст товар дважды.
3. **Переключатель статусов** на странице заказа существует только для демонстрации.
   На бою статус меняют платёжная система и админ.
4. **Валидация форм.** Сейчас она только на клиенте — на бою нужна серверная, плюс
   rate limiting и Turnstile на checkout и в поддержке.
5. **Авторизация.** `/login` и `/register` ничего не отправляют.

Пароль от Roblox не запрашивается нигде и не должен появиться ни в одном сценарии.

## Товарные знаки

Roblox и Robux — знаки Roblox Corporation, проект с ней не связан. Скачанные чужие
иконки лежат отдельно в `public/brand/third-party/` (источник — simple-icons, CC0),
чтобы их можно было заменить одним движением. Монета номинала и знак RBXDrop
нарисованы для этого проекта и чужих знаков не повторяют.

## Чего в макете нет

Админка `/admin`, база данных, авторизация, платежи, реальная выдача Robux, почта.
